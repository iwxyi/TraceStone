# TraceStone AI 模块设计

## 1. 模块定位

TraceStone 的 AI 模块不是单篇日记点评器，而是一个本地优先、可持续生长的个人认知系统。它需要在尊重当前文本的前提下，检索用户自己的历史记忆、关系记录、行动记录与长期画像，生成温和、具体、可验证的洞察。

AI 模块服务多个场景：

| 场景 | 当前输入权重 | 历史记忆权重 | 输出重点 |
| --- | --- | --- | --- |
| 今日洞察 | 最高 | 辅助 | 围绕今天这篇日记生成读后感、关联记忆、塑石建议 |
| 成长陪伴问答 | 取决于用户问题 | 最高 | 基于个人历史回答问题，必要时追问 |
| 月/年总结 | 周期内日记最高 | 长期记忆辅助 | 总结阶段性模式、变化、行动线索 |
| 全局搜索 | 查询最高 | 最高 | 找到相关日记、记忆、人物和总结 |
| 关系洞察 | 相关人物最高 | 辅助 | 解释互动模式与关系变化 |

因此，AI 模块应拆成可复用的能力：结构化抽取、记忆检索、上下文组装、洞察生成、记忆更新。

## 2. 核心原则

1. 当前任务的主材料必须优先。  
   今日洞察必须以今日日记为主；月报以本月为主；问答以用户问题为主。

2. 历史只能辅助，不能覆盖当前表达。  
   如果历史记忆和当前日记冲突，AI 应承认变化，而不是强行套用旧画像。

3. 只能引用已检索到的材料。  
   AI 不得凭空说“你一直以来都……”除非上下文中有证据。

4. 记忆更新必须小步、可追溯。  
   用户画像和关系档案不应被单篇日记大幅改写，必须记录证据、日期和置信度。

5. 建议必须可执行。  
   塑石建议要小、具体、明天可做，不做空泛说教。

6. 保留用户语言风格。  
   修复错字和语病时不改写情绪、不美化、不替用户下判断。

7. 区分事实、信号、推测和建议。  
   AI 可以观察模式，但不能把推测包装成事实。凡是超出原文直接描述的内容，都应明确为“可能”“看起来”“也许值得留意”。

8. 输出必须可解释。  
   重要结论应能追溯到当前日记、历史摘要、记忆、画像或关系档案中的具体来源。

## 3. 日记结构理解

一篇日记可能包含多个事件，而不是一个单一主题。用户可能用分割线、标题、空行、列表或自己的习惯组织内容，例如：

```markdown
# 今天

早上开会很累。

---

晚上去健身，状态还不错。

---

吃了火锅，有点撑。
```

AI 分析前应先做结构化切分：

| 单元 | 识别方式 |
| --- | --- |
| 标题段 | Markdown 标题、首行标题、用户自定义明显标题 |
| 分割段 | `---`、`***`、长横线、连续空行 |
| 列表段 | `-`、`*`、数字列表 |
| 事件段 | 同一时间、人物、地点、活动构成的片段 |
| 元数据 | 日期、地点、天气、温度、图片描述 |

推荐生成 `DiarySegment`：

```json
{
  "segmentId": "entryId#s1",
  "title": "健身",
  "text": "晚上去健身，状态还不错。",
  "topics": ["健康", "运动"],
  "people": [],
  "emotion": "轻松",
  "importance": 0.62
}
```

今日洞察应同时给出整体判断和分段理解，避免一件小事覆盖整篇日记。

## 4. 记忆分层

### 4.1 原始日记

不可改写的事实源。所有洞察、画像、关系都应能追溯到原始日记。

### 4.2 日记片段记忆

从单篇日记拆出的事件或主题片段，适合语义检索。

字段建议：

```json
{
  "id": "segmentId",
  "entryId": "diaryEntryId",
  "date": "2026-07-03",
  "summary": "晚上完成了健身，状态不错。",
  "topics": ["健康", "运动"],
  "people": [],
  "emotion": "轻松",
  "embedding": [0.01, 0.02]
}
```

### 4.3 长期记忆

从多篇日记中沉淀的稳定信息，例如长期偏好、反复困扰、重要转折。

长期记忆应有证据链：

```json
{
  "id": "memory_x",
  "summary": "用户在压力大时倾向于通过运动恢复状态。",
  "tags": ["压力", "运动", "自我调节"],
  "evidenceEntryIds": ["e1", "e7", "e19"],
  "confidence": 0.76,
  "updatedAt": "2026-07-03"
}
```

### 4.3.1 记忆生命周期

记忆不是越多越好。所有长期记忆都应有生命周期字段，避免记忆库越来越吵。

```json
{
  "id": "memory_x",
  "summary": "用户在压力大时倾向于通过运动恢复状态。",
  "importance": 0.72,
  "confidence": 0.76,
  "evidenceEntryIds": ["e1", "e7", "e19"],
  "createdAt": "2026-05-01",
  "updatedAt": "2026-07-03",
  "lastReferencedAt": "2026-07-03",
  "referenceCount": 4,
  "decay": 0.12,
  "archived": false
}
```

| 字段 | 作用 |
| --- | --- |
| `importance` | 决定是否值得进入上下文 |
| `confidence` | 判断是否足够稳定，可否影响画像 |
| `lastReferencedAt` | 长期未引用的记忆可降权 |
| `referenceCount` | 多次命中的记忆更可信 |
| `decay` | 控制旧记忆自然降权 |
| `archived` | 低价值或过时记忆归档，不默认检索 |

记忆降权不等于删除。用户仍可通过搜索找到，但默认洞察不应被低价值旧记忆干扰。

### 4.4 用户画像

用户画像是长期记忆的压缩视图，更新频率应低于普通记忆。

建议分区：

| 分区 | 示例 |
| --- | --- |
| 价值观 | 重视稳定、自由、亲密关系、成长 |
| 压力源 | 工作汇报、家庭冲突、身体状态 |
| 调节方式 | 运动、独处、写作、散步 |
| 建议偏好 | 喜欢具体小步骤，不喜欢鸡汤 |
| 生活节律 | 晚上更容易反思，周末更关注关系 |

画像更新必须采用候选机制，而不是单次分析直接覆盖：

```json
{
  "field": "stress_pattern",
  "value": "工作汇报可能是压力源",
  "evidence": [
    {"type": "entry_summary", "id": "summary_1"},
    {"type": "memory", "id": "memory_7"}
  ],
  "confidence": 0.58,
  "action": "candidate"
}
```

只有当多个证据在不同时间重复出现，置信度达到阈值后，才合并进稳定画像。

### 4.5 关系档案

人物不只是标签，需要独立档案：

```json
{
  "personId": "p_mom",
  "names": ["妈妈", "母亲"],
  "relationship": "family",
  "recentInteractions": [
    {"date": "2026-07-03", "summary": "因为安排产生争执", "emotion": "委屈"}
  ],
  "patterns": ["沟通时容易因边界感产生压力"]
}
```

### 4.6 塑石行动记录

记录建议、采纳、完成情况，以及后续日记是否提到相关行动。

这让 AI 能说：“我注意到你今天真的去做了上次说的那一步。”

## 5. 关联信息来源

分析当前日记时可检索以下上下文：

| 来源 | 作用 | 注意事项 |
| --- | --- | --- |
| 最近日记 | 判断最近状态 | 不要超过必要数量 |
| 语义相关片段 | 找类似事件 | 需返回相关理由 |
| 长期记忆 | 提供稳定模式 | 必须带证据 |
| 用户画像 | 调整语气和建议 | 不可替代当前文本 |
| 关系档案 | 解释人物互动 | 避免给关系下绝对结论 |
| 塑石行动 | 判断进展 | 不要批评用户未完成 |
| 去年今日/多年今日 | 体现成长性 | 阳历和农历都要考虑 |

## 6. 历史日记引用策略

历史日记不应默认以全文形式进入上下文。全文会消耗大量 token，也会引入很多与当前问题无关的噪声。推荐每篇日记在保存或分析后生成一个可检索、可引用的摘要包。

### 6.1 日记摘要包

每篇日记应生成 `EntrySummary`：

```json
{
  "entryId": "entry_x",
  "date": "2026-07-03",
  "title": "今天的几个片段",
  "brief": "今天主要记录了工作会议、晚间健身和饮食状态。",
  "keyPoints": [
    "早上会议让用户感到疲惫。",
    "晚上健身后状态有所恢复。",
    "晚餐吃得较多，身体有些负担。"
  ],
  "importantQuotes": [
    "跑完以后感觉整个人松了一点。"
  ],
  "topics": ["工作", "健身", "饮食"],
  "people": [],
  "emotion": "疲惫后放松",
  "importance": 0.68
}
```

其中：

| 字段 | 用途 |
| --- | --- |
| `brief` | 用于普通历史上下文，最省 token |
| `keyPoints` | 用于保留多个事件，不丢失结构 |
| `importantQuotes` | 只保存非常关键的原文短句 |
| `topics/people/emotion` | 用于检索和重排 |
| `importance` | 用于决定是否进入上下文 |

### 6.2 引用优先级

历史上下文建议按以下优先级引用：

1. 摘要包 `brief/keyPoints`
2. 重要原文短句 `importantQuotes`
3. 日记片段摘要 `DiarySegment.summary`
4. 必要时才读取原文全文

也就是说，AI 默认看到的是“压缩后的历史”，只有当用户明确追问、检索结果极其相关、或需要验证细节时，才展开原文。

### 6.3 摘要更新

摘要包不是一次性生成后永久不变。它应在以下情况更新：

| 情况 | 动作 |
| --- | --- |
| 日记正文被编辑 | 重新生成该篇摘要和片段 |
| AI 分析协议升级 | 后台或下次访问时迁移 |
| 用户手动标记重要 | 提升 importance，保留更多原文片段 |
| 多次被引用 | 提升该摘要的长期价值 |

### 6.4 降噪原则

历史摘要进入上下文时，应避免“每篇都同等展示”。推荐压缩为：

```text
相关历史摘要：
1. 2025-07-03｜健身后状态恢复｜和今天同样出现“运动缓解疲惫”
2. 2024-端午｜家庭聚餐压力｜同属农历节日家庭互动
```

这样可以容纳更多记录，同时减少模型被无关原文带偏。

## 7. 证据引用与结论分层

AI 输出中的重要结论应当带来源。普通用户可以看到自然语言版，开发者模式可以看到完整来源。

### 7.1 证据引用

建议统一证据结构：

```json
{
  "type": "entry_summary",
  "id": "summary_2025_07_03",
  "date": "2025-07-03",
  "quote": "跑完以后感觉整个人松了一点。",
  "summary": "用户记录运动后压力下降。",
  "relevance": "与今天健身后状态改善相关"
}
```

证据来源类型：

| 类型 | 示例 |
| --- | --- |
| `current_entry` | 当前日记原文或片段 |
| `entry_summary` | 历史日记摘要 |
| `segment` | 历史日记片段 |
| `memory` | 长期记忆 |
| `profile` | 用户画像 |
| `relationship` | 关系档案 |
| `stone` | 塑石任务或打卡 |
| `calendar` | 阳历/农历/节日关联 |

### 7.2 事实、信号、推测、建议

AI 结果应区分：

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| `facts` | 当前日记或历史材料明确写到的事实 | “今天晚上去健身。” |
| `signals` | 从文本中较稳妥识别出的情绪/主题 | “疲惫后有恢复感。” |
| `hypotheses` | 需要谨慎表达的模式推测 | “运动可能是你近期有效的调节方式。” |
| `suggestions` | 可执行建议 | “明天晚饭后散步 10 分钟。” |

这样可以防止 AI 把“猜测”说成“你就是这样的人”。

### 7.3 反证与变化

如果新日记和旧画像/旧记忆不一致，不应强行忽略。应生成反证候选：

```json
{
  "oldMemoryId": "memory_social_avoidance",
  "newEvidence": "今天和朋友聚会后感觉很放松。",
  "interpretation": "这可能说明用户近期的社交状态在恢复，旧记忆需要降权或增加条件。",
  "confidence": 0.64
}
```

反证处理建议：

| 情况 | 动作 |
| --- | --- |
| 单次反证 | 只记录候选，不改画像 |
| 多次反证 | 降低旧记忆 confidence |
| 明确用户纠正 | 立即更新或归档旧记忆 |
| 长期变化 | 生成新的长期记忆，并保留变化轨迹 |

## 8. “去年今日”和多年关联

“去年今日”不应只看上一年同一天。为了体现成长性，应支持多年历史对照。

### 8.1 阳历今日

检索所有历史年份的同月同日：

```text
2026-07-03 今日
2025-07-03
2024-07-03
2023-07-03
```

### 8.2 农历今日

节日和生日可能按农历发生，例如端午、中秋、春节、农历生日。

需要保存或计算：

| 类型 | 示例 |
| --- | --- |
| 农历日期 | 五月初五 |
| 农历节日 | 端午 |
| 用户自定义纪念日 | 外婆生日 |

分析时可以检索：

```text
今年端午的日记
去年端午的日记
过去所有端午附近的日记
```

### 8.3 时间窗口

历史关联不应只精确匹配当天，也要支持窗口：

| 场景 | 窗口 |
| --- | --- |
| 阳历今日 | 同月同日，外加前后 1 天可选 |
| 农历节日 | 同一农历节日 |
| 周期性事件 | 前后 3-7 天 |
| 长期成长对照 | 多年同主题，而不局限同日 |

## 9. 关联程度怎么计算

不要只用一种方式。推荐混合检索：向量为主，结构化特征和时间特征校准。

### 9.1 为什么不能只做语义文本比较

纯文本语义相似能找到“意思接近”的日记，但容易忽略：

- 同一个人名
- 同一个地点
- 同一个节日
- 同一个行动任务
- 同一个长期模式
- 时间上的连续性

### 9.2 为什么要做多种向量

一篇日记可能有多个事件。整篇日记一个向量会把多个主题混在一起。

例如：

```markdown
早上开会很烦。

---

中午吃了火锅。

---

晚上健身后心情好了。
```

如果只存整篇日记向量，它会变成“工作压力 + 饮食 + 健身恢复”的混合表示。之后搜索“运动缓解压力”可能能找到，但精度不稳定；搜索“火锅吃撑了”也可能被工作和健身内容稀释。

因此，整篇向量有用，但不能替代分段向量。

建议至少三类向量：

| 向量 | 内容 | 用途 |
| --- | --- | --- |
| entry embedding | 整篇日记摘要 | 找整体相似日记、周期总结、粗召回 |
| segment embedding | 每个事件片段 | 找具体相关事件，避免多事件互相稀释 |
| summary embedding | 日记摘要包 | 降噪检索，适合历史引用 |
| memory embedding | 长期记忆摘要 | 找稳定模式 |

后续可增加：

| 向量 | 用途 |
| --- | --- |
| person interaction embedding | 找相似关系互动 |
| stone action embedding | 找行动进展 |
| profile embedding | 找画像相关问题 |

### 9.2.1 分段向量策略

一篇日记应尽量拆成多个语义片段，再分别生成向量。

优先级：

1. 用户显式结构  
   Markdown 标题、分割线 `---` / `***`、列表、空行分段。

2. 时间结构  
   “早上 / 中午 / 下午 / 晚上 / 睡前 / 今天先是 / 后来”等。

3. 事件结构  
   人物、地点、行为、情绪明显变化。

4. 主题结构  
   工作、家庭、饮食、健身、情绪、关系等主题切换。

推荐规则：

| 情况 | 处理 |
| --- | --- |
| 用户用了分割线 | 优先按分割线切段 |
| 有 Markdown 标题 | 标题和其下内容合为一段 |
| 段落太短 | 与相邻段合并 |
| 段落太长 | 再按语义或自然段切分 |
| 内容混杂多个事件 | 拆成多个 segment |
| 只有一句简短日记 | 保留一个 segment |

片段长度建议：

| 长度 | 建议 |
| --- | --- |
| 少于 30 中文字 | 通常太短，考虑合并 |
| 100-500 中文字 | 比较适合生成 segment embedding |
| 超过 800 中文字 | 考虑继续切分 |

每个片段保存：

```json
{
  "segmentId": "entryId#s2",
  "entryId": "entryId",
  "order": 2,
  "title": "晚上健身",
  "text": "晚上健身后心情好了。",
  "summary": "晚上健身后状态恢复。",
  "topics": ["健身", "情绪调节"],
  "people": [],
  "emotion": "放松",
  "importance": 0.74,
  "embedding": [0.01, 0.02]
}
```

### 9.2.2 多层级召回顺序

检索时不建议只查一种向量。推荐：

```text
1. segment embedding：先找具体事件
2. memory embedding：找长期模式
3. summary embedding：找历史日记摘要
4. entry embedding：补充整体相似日记
5. profile / relationship / stone：按场景补充结构化上下文
```

今日洞察尤其应优先查 segment，因为今天的某个事件可能只对应历史中的某个小片段，而不是整篇日记。

### 9.2.3 向量粒度的取舍

| 粒度 | 优点 | 风险 |
| --- | --- | --- |
| 整篇日记向量 | 简单、便宜、适合整体相似 | 多事件会被平均化 |
| 片段向量 | 精准、适合事件关联 | 片段太碎会增加噪声 |
| 摘要向量 | 降噪、省 token | 摘要质量影响召回 |
| 长期记忆向量 | 适合模式识别 | 更新策略要谨慎 |

因此，最佳实践是“多层级召回 + 重排”，不是只选择一种。

### 9.3 推荐评分公式

最终相关度不直接等于向量相似度，而是加权：

```text
score =
  0.50 * semantic_similarity
  + 0.15 * people_overlap
  + 0.10 * topic_overlap
  + 0.10 * time_relevance
  + 0.08 * emotion_similarity
  + 0.07 * action_or_relation_match
```

不同场景权重不同：

| 场景 | 权重倾向 |
| --- | --- |
| 今日洞察 | 当前日记主题、人物、最近状态更重要 |
| 问答 | 用户问题语义相似更重要 |
| 月/年总结 | 时间范围内覆盖率更重要 |
| 搜索 | 语义相似和过滤条件更重要 |
| 关系洞察 | 人物匹配权重最高 |

### 9.4 检索流程

```text
用户输入/当前日记
  ↓
结构化抽取：人物、主题、情绪、事件段
  ↓
生成 query embeddings
  ↓
多路召回：
  - segment 向量
  - memory 向量
  - person 关系
  - 时间/节日关联
  - 塑石行动
  ↓
重排 rerank
  ↓
压缩成 Memory Context
  ↓
交给 LLM 生成结果
```

### 9.5 重排解释

召回后的结果必须经过 rerank，并记录命中原因。不要只保存一个分数。

```json
{
  "sourceId": "summary_2025_07_03",
  "finalScore": 0.82,
  "signals": {
    "semantic": 0.77,
    "peopleOverlap": 0.0,
    "topicOverlap": 0.9,
    "timeRelevance": 0.4,
    "emotionSimilarity": 0.7,
    "calendarMatch": 0.3
  },
  "reasons": [
    "同主题：运动与恢复状态",
    "情绪相似：疲惫后放松",
    "多年今日附近"
  ]
}
```

普通用户只看到自然语言原因；开发者模式显示分数明细。

## 10. 分阶段 AI Pipeline

不要把所有任务塞进一个大 prompt。推荐拆成多个阶段，每阶段输出结构化结果。

触发时机应是“用户明确退出编辑并保存”之后，而不是编辑过程中的实时自动保存。实时自动保存只保证正文不丢；AI Pipeline 属于保存后的后台工作，不能阻塞用户离开编辑页。

```text
Extract
  ↓
Retrieve
  ↓
Rerank
  ↓
Generate
  ↓
Update
```

### 10.1 Extract

输入当前日记，输出：

- 分段
- 事实
- 人物
- 地点
- 主题
- 情绪信号
- 重要度

### 10.2 Retrieve

用 Extract 结果做多路召回：

- entry summary
- segments
- long-term memories
- user profile
- relationship profiles
- calendar context
- stone actions

### 10.3 Rerank

融合向量分数、结构化匹配、时间、情绪、人物、节日等因素，输出带解释的候选上下文。

### 10.4 Generate

根据当前任务生成结果：

- 今日洞察
- 问答
- 搜索解释
- 月/年总结

Generate 阶段不应直接更新长期记忆，只输出 update candidates。

### 10.5 Update

独立处理：

- 写入日记摘要
- 写入片段
- 写入长期记忆
- 生成画像候选
- 更新关系档案候选
- 记录反证

这样可以让生成结果和记忆写入解耦，降低误写入风险。

### 10.6 后台任务队列

AI Pipeline 应由持久化后台队列驱动，而不是由页面生命周期直接驱动。每篇日记对应一个或多个可恢复 job。

推荐 job 状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 已入队，尚未开始 |
| `running` | 当前正在处理 |
| `incomplete` | App 被杀、Web 标签页关闭、系统中断等导致未完成 |
| `failed` | 明确失败，例如模型不可用、解析失败、网络错误超过重试次数 |
| `completed` | 所有必要阶段完成 |

每个 job 保存：

- `entryId`
- `pipelineVersion`
- `currentStage`
- `completedStages`
- `retryCount`
- `lastError`
- `updatedAt`
- 阶段产物引用，例如 summaryId、segmentIds、embeddingIds

原则：

- 阶段要幂等，可重复执行。
- 每完成一个阶段就落库，避免整条 Pipeline 因中断全部重来。
- App 启动、回到前台、网络恢复、设备空闲时，都可以扫描 `pending/incomplete/failed retryable` job 继续执行。
- 如果中断发生在 `running` 状态，下次启动时先把超时的 `running` 标记为 `incomplete`，再继续。
- 同一篇日记重新编辑保存后，应废弃旧版本未完成 job，创建新 `pipelineVersion` 的 job。

### 10.7 串行处理与导入场景

多篇日记默认串行处理，一次只跑一个 AI job。原因：

- 移动端内存和温控更稳定。
- 避免向量模型、LLM 请求、数据库写入同时抢资源。
- 未来批量导入几千篇日记时，串行队列更容易暂停、恢复和展示进度。

导入场景应分批入队，但不并行执行。首页或导入页只展示整体进度：

```text
正在整理 3/1280 篇
当前阶段：生成摘要
可随时退出，下次打开会继续
```

### 10.8 首页生成卡片

首页可以有一张轻量的“正在整理记忆”卡片，但它展示的是队列状态，而不是页面临时状态。

普通模式建议展示：

- 当前正在处理的日记日期或标题
- 当前阶段的自然语言说明，例如“正在生成摘要”“正在关联历史记录”
- 剩余数量
- 暂停/继续入口可后置到高级设置，初期不必暴露

开发者模式额外展示：

- job id
- pipeline version
- stage 耗时
- retry 次数
- last error
- 当前输入/输出摘要

## 11. 今日洞察上下文组装

今日洞察必须以今天为主。推荐上下文比例：

| 内容 | 预算 |
| --- | --- |
| 当前日记原文 | 40%-50% |
| 当前日记分段结构 | 15% |
| 最近状态 | 10%-15% |
| 相关历史记忆 | 15%-20% |
| 用户画像/关系/塑石 | 10%-15% |

历史材料优先使用摘要包和片段摘要，不直接塞入大量原文。当前日记原文可以完整提供，历史原文只在必要时局部展开。

提示词应明确：

```text
你正在分析“今日”这篇日记。
当前日记是主材料，历史材料只能作为辅助。
如果历史材料不足，不要强行引用。
如果当前日记包含多个事件，请分别理解，再给出整体读后感。
```

## 12. 跨场景复用

同一套记忆系统服务多个入口，但上下文组装策略不同。

### 12.1 今日洞察

输入：当前日记。  
输出：读后感、关联记忆、情绪、关键词、人物、塑石建议、记忆更新。

### 12.2 洞察问答

输入：用户问题。  
输出：回答、引用历史、追问。

问答时“今天”不一定重要，除非用户问题涉及今天。

### 12.3 月/年总结

输入：时间范围。  
输出：阶段主题、情绪变化、关系变化、塑石进展、代表日记。

月/年总结不能只拼接单篇洞察，应先做周期内聚合。

### 12.4 搜索

输入：自然语言查询和筛选条件。  
输出：相关日记、片段、记忆、人物。

搜索结果需要可解释：为什么匹配。

## 14. 开发者模式与可解释性

普通用户不应被大量检索分数、来源 ID、原始 JSON 干扰。建议在设置中增加“开发者模式”开关。

### 14.1 普通模式

普通模式只展示简洁结果：

- 今日读后感
- 关联记忆的自然语言说明
- 塑石建议
- 必要的标签和情绪

例如：

```text
这让我想起你去年夏天也写过一次运动后变轻松的感觉。
```

不展示：

- embedding 分数
- rerank 明细
- sourceId
- prompt
- raw JSON
- token 使用量

### 14.2 开发者模式

开启后，可在洞察详情、搜索结果、总结结果中查看：

| 信息 | 用途 |
| --- | --- |
| 检索来源 | 验证 AI 引用了哪些日记、片段、记忆 |
| 摘要包内容 | 检查历史压缩是否准确 |
| 向量相似度 | 调试语义召回 |
| rerank 分数 | 解释为什么某条历史更相关 |
| prompt 摘要 | 检查上下文组装 |
| raw JSON | 调试解析和协议 |
| memory/profile updates | 验证记忆和画像更新 |
| contradictions | 验证反证与画像修正 |
| pipeline stages | 查看 Extract/Retrieve/Rerank/Generate/Update 每阶段结果 |
| job queue | 查看 pending/running/incomplete/failed/completed 队列 |
| stage logs | 查看每个阶段的输入摘要、输出摘要、错误和重试 |
| embedding metadata | 查看模型版本、向量维度、生成时间和关联对象 |
| token/耗时 | 优化性能和成本 |

开发者模式可以显示类似：

```text
引用来源
- entry_2025_07_03，score 0.82
  原因：同主题“运动恢复状态”，同季节，情绪相似
  摘要：去年夏天用户提到跑步后压力下降
```

### 14.3 数据边界

即使开启开发者模式，也应遵守：

- 不上传额外数据。
- 不展示系统密钥。
- 不把 prompt/debug 信息同步到后端。
- debug 信息默认本地保存，可清除。

### 14.4 设置项建议

```text
设置 > 高级 > 开发者模式
```

开启后额外出现：

- 显示 AI 引用来源
- 显示检索分数
- 显示原始 JSON
- 导出本次分析上下文
- 查看后台 AI 队列
- 查看失败/未完成任务
- 重新运行某篇日记的摘要、分段、向量或洞察

开发者模式的目标是调试和验证，不追求轻量。只要不泄露密钥、不额外上传数据，可以显示较重的信息，包括完整来源链、阶段产物、重试日志和模型元数据。

主要剩余差距：

1. 当前 embedding 仍是本地 hashing 方案，适合验证管线，不等于最终高质量中文语义模型。
2. 还没有接入 ObjectBox Vector Search 或其它成熟向量索引；当前适合中小规模数据。
3. 分段主要是规则实现，已支持常见时间词和本地语义转场拆分同段多事件；还没有真正由 AI 判断隐式事件边界的语义分段。
4. 农历关联已有常见节日和自定义农历纪念日的查表匹配；还需要完整农历日期计算、范围更长的年份覆盖和索引缓存。
5. 画像和关系档案已有候选、投影、确认、修正、隐藏、冲突解释和开发者决策清单；还需要把候选合并与冲突处理变成更完整的用户决策流程。
6. `ProfileFact`、`RelationshipProfile` 和塑石行动已有第一版独立 embedding，并会在搜索时补建、刷新和清理失效索引；还需要更成熟的向量索引。
7. 当前 AI Pipeline 仍以单个 job 串起多个阶段；开发者模式已有局部重建入口，未来可进一步拆成更细粒度、可排队调度的子任务。
8. 批量导入几千篇日记时，已有队列暂停/继续、批次分组和耗时估算的第一版 UI；还需要导入页分批入队入口和更精确的耗时校准。
9. 历史摘要目前以本地规则摘要为主，已支持用户修正摘要包、修订版本和修正时间；未来需要可选 AI 摘要生成、摘要质量评估和更完整的版本历史。
10. 开发者模式已有 AI 衍生数据清单和导出提示；隐私、备份、导出策略还需要接入实际备份加密与同步边界。

## 17. 实现前待讨论清单

以下细节会影响 AI 模块的准确性、性能和可维护性，建议正式实现前逐项确认。

### 17.1 分段边界

需要确定：

- 分割线是否一定代表不同事件。
- Markdown 标题是否一定开启新 segment。
- 连续短段落如何合并。
- 列表是整体作为一段，还是每个 item 单独成段。
- 图片描述、语音转写、位置天气是否进入 segment 文本。
- 用户手动修改日记后是否立即重建所有 segment。

建议：先实现规则分段，再逐步加入 AI 语义分段。规则分段可解释、可控，也便于调试。当前规则分段已覆盖 Markdown 标题、分割线、自然段和“早上/中午/晚上/睡前”等时间词；下一步再处理没有显式边界、但语义上明显是不同事件的长段落。

### 17.2 摘要质量

摘要包会成为历史引用的主材料，因此质量很关键。

需要确定：

- 摘要是否由 AI 生成，还是先用规则截取。
- 摘要是否允许使用原文短句。
- 重要原文引用最多保存几条。
- 摘要是否保留用户原本的语气。
- 用户是否可以手动编辑某篇日记的摘要。

建议：摘要分为 `brief` 和 `keyPoints`，`brief` 用于快速上下文，`keyPoints` 保留多事件结构。

### 17.3 向量模型

需要确定：

- 使用哪一个本地 embedding 模型。
- 中文语义效果是否足够。
- 模型大小、加载时间、内存占用是否可接受。
- 是否需要在设备空闲时批量生成向量。
- 老数据如何补建向量。

建议：

- 先封装 `EmbeddingService`，不要让业务层直接依赖具体模型。后续模型替换时只改服务实现。
- 模型选择在性能和准确度之间均衡，但略偏向准确度。日记通常不会特别长，向量生成又可以后台串行执行，因此不必为了极致速度牺牲中文语义效果。
- 必须记录 `embeddingModelId`、`embeddingVersion`、维度、生成时间，方便以后重建向量和调试召回质量。
- 向量生成不要阻塞保存，也不要阻塞用户退出编辑页。

### 17.4 向量更新时机

需要确定：

- 用户明确退出编辑并保存后，由后台队列生成。
- 编辑日记后是否同步删除旧 segment/vector。
- AI 分析失败时是否仍生成基础摘要和向量。
- 离线状态下如何排队。

建议：日记保存后先写入原文，再入队生成 summary/segment/vector/status。UI 显示“分析中”或由首页生成卡片展示队列进度。实时自动保存不触发完整 AI Pipeline。

队列执行顺序建议：

1. 生成摘要包。
2. 规则分段和语义分段。
3. 生成 entry/summary/segment 多级向量。
4. 检索历史上下文。
5. 生成今日洞察。
6. 产出长期记忆、画像、关系档案的候选更新。

如果任一阶段被系统中断，标记为 `incomplete`，下次启动继续。只有明确不可恢复的错误才标记为 `failed`。

### 17.5 检索预算

需要确定每次分析最多取多少历史材料。

建议初始值：

| 类型 | 数量 |
| --- | --- |
| recent entries | 5-10 |
| segment results | 8-12 |
| memory results | 5-8 |
| profile items | 3-5 |
| relationship items | 3-5 |
| calendar matches | 3-8 |

这些数量应按场景调整，今日洞察不要让历史上下文超过当前日记。

### 17.6 用户可控性

用户应该能控制 AI 记忆。

需要考虑：

- 某条长期记忆是否可删除/隐藏。
- 用户能否纠正画像。
- 用户能否查看 AI 记住了什么。
- 日记进入回收站和永久删除时，关联 summary/vector/memory 分别如何处理。

当前决策：不提供单篇日记“不要进入记忆”标记。日记进入 AI 系统是产品默认行为，否则记忆连续性和检索一致性会变复杂。

建议：后续增加“记忆管理”入口，让用户管理长期记忆、画像和关系档案；初期至少保证删除日记时清理衍生数据。

删除生命周期：

- 删除日记先进入回收站。
- 回收站入口放在设置中。
- 回收站保留 90 天，超过后自动永久删除。
- 回收站内日记默认不参与新的检索、总结和画像更新。
- 永久删除时清理正文、摘要、片段、向量、调试日志和可追溯到该日记的候选记忆。
- 如果某条长期记忆由多篇日记共同支撑，删除其中一篇时只移除该来源；当来源为空或证据不足时再降级、隐藏或删除该记忆。

### 17.7 隐私与本地优先

AI 上下文里会包含高度私密内容。

需要确认：

- 自定义 Key 调用时，哪些内容会发给第三方模型。
- 官方服务是否只做转发，不存明文。
- 开发者模式导出的上下文是否有明显隐私提示。
- WebDAV 备份是否包含 summary/vector/debug 数据。

建议：所有衍生数据默认视为日记数据的一部分，遵守同样的备份、删除、加密策略。

### 17.8 UI 呈现

普通用户不需要看到复杂结构。

需要确定：

- 关联记忆如何展示才自然。
- “为什么 AI 这么说”是否默认折叠。
- 开发者模式入口放在哪里。
- 反证/画像更新是否提示用户确认。
- AI 分析结果是否允许用户反馈“不准确”。

建议：普通模式展示“关联记忆”和“塑石建议”；开发者模式才显示分数、来源、pipeline。

### 17.9 失败与降级

需要明确 AI 或向量能力不可用时如何降级。

| 失败点 | 降级 |
| --- | --- |
| embedding 模型不可用 | 使用关键词检索 |
| AI 分析失败 | 保留日记，标记待分析 |
| summary 生成失败 | 使用 bodyPreview 临时摘要 |
| vector 写入失败 | 只保存结构化摘要 |
| 关系识别失败 | 不更新关系档案 |

AI 模块不能阻塞日记保存。
